# 通勤与商圈推荐算法

推荐的目标是：在内置约饭商圈中，根据本次参加朋友的出发点、各自选择的地铁或驾车方式、个人通勤优先级和选定策略，比较通勤估计时间。地铁路线与推荐评分在浏览器内计算；驾车可使用服务端返回的高德道路路线，等待结果或请求失败时使用离线粗估。修改权重不需要重新请求远程路线 API。

## 保存朋友与本次参加

朋友列表可保存 0–50 人，每人以 `enabled` 记录本次是否参加；只有 `enabled: false` 表示不参加，缺失字段的旧方案默认全部参加。读取保存数据时，非法的非布尔值也回退到参加状态，保留原有地址、坐标、交通方式和权重。空朋友列表是有效的保存状态，不会自动恢复默认朋友。

`getParticipatingFriends(friends)` 保持原列表顺序筛选本次参加者。`rankDistricts` 在计算前使用这个筛选结果，人数不足两人时返回空推荐列表，由界面引导选择朋友。不参加者仍保存在朋友列表里，但不产生本次路线，不影响可达性、加权分数、平均与最长时间或驾车路线覆盖情况。再次参加后，沿用原有出发地点、交通方式和权重重新比较商圈。单人 `planRoute` 独立接受任何朋友，是否参加仅约束群体推荐。

## 数据与坐标

`src/lib/data/metro.json` 保存了 2026-09-13 08:18:23 UTC 抓取的 [高德深圳公开地铁图数据](https://map.amap.com/service/subway?_1469083453978&srhdata=4403_drw_shenzhen.json)，包含 351 座去重车站、16 组线路。2 / 8 号线按贯通线路处理，6 号线支线单独处理；坪山云巴不在地铁图计算范围内。数据源的原始坐标为 GCJ-02，更新脚本以迭代反算统一为 WGS84。

抓取时间说明这份文件何时取得，不代表数据源一定包含当天的全部运营变化。可对照 [深圳地铁官方运营线路图](https://www.szmc.net/shentieyunying/yunyingfuwu/szsgdjtyyxlwlt/)核查。程序不根据抓取日期推断运营状态。

`src/lib/data.ts` 维护候选商圈、介绍及默认朋友。商圈中心按附近地铁站做近似偏移，不是餐厅门牌或商场入口；地图商圈圆形范围是视觉参考，不是可达等时圈。站间几何由相邻站点连接，展示线路关系，不代表准确轨道走向。

更新地铁数据：

```sh
bun run update:metro
bun run check
bun run test
bun run build
```

更新脚本会检查城市、线路和坐标，以及最少站点数量，避免用明显残缺的数据覆盖快照。更新后应人工检查新增线路、站名变化、换乘关系和默认商圈锚点，再提交脚本与数据差异。

## 每人的地铁路线

朋友字段 `travelMode` 可取 `transit` 或 `driving`，默认 `transit`；旧保存对象没有此字段时也按地铁处理。每人独立选择交通方式，同一推荐可以同时包含地铁与驾车朋友。

路由图按“车站 + 所在线路”建模。同一个换乘站在不同线路上有不同状态；同线相邻站之间有双向边，线路之间有换乘边。这样能分别累计乘车时间和换乘成本，不会把换乘当成零分钟。

对起点和每个商圈中心，分别选择直线距离 1.6 公里内最近的最多六个地铁站作为接驳候选。Dijkstra 搜索比较到站步行、进站、候车、乘车、换乘、出站及最后步行的总时间，保留候选路线中最短的一条。因此较近的进站口不一定胜出：稍多走一段，可能省下换乘。

起点与商圈中心的直线距离不超过 1.6 公里时，也比较直接步行方案；直接步行更快则显示纯步行。地铁方案需要实际经过线路边，不会把同一个站的进出站当作一次乘车。没有满足步行接驳条件的路线时，返回 `reachable: false`；任何一位本次参加朋友不可达的商圈得分为无穷大，界面只展示得分有限的推荐。所有商圈都不可达时会提示检查出发地点。这里的“不可达”只表示模型找不到符合条件的方案，不等于真实世界无法到达。

| 模型参数             | 取值                                |
| -------------------- | ----------------------------------- |
| 步行距离             | 球面直线距离 × 1.25 绕行系数        |
| 步行速度             | 4.6 公里 / 小时                     |
| 起点、终点的接驳候选 | 各最多六站，直线距离不超过 1.6 公里 |
| 进站 / 出站          | 各两分钟                            |
| 首次候车             | 三分钟                              |
| 普通换乘             | 六分钟，包含步行与平均候车          |
| 大型枢纽换乘         | 八分钟                              |
| 普通线路运行速度     | 42 公里 / 小时                      |
| 11 / 14 号线运行速度 | 62 公里 / 小时                      |
| 相邻站运行附加时间   | 一分钟 / 站间边                     |
| 单条站间边最低时间   | 1.8 分钟                            |

大型枢纽在实现中为深圳北站、岗厦北、福田、车公庙、布吉和大运。相邻站时间取 `max(1.8, 直线距离 / 线路速度 × 60 + 1)`。这些数值是用于比较地点的模型假设，未按真实班次、时段、方向或车站实测校准。路线估计不会查询首末班车；同一段线路在同一组参数下的时间固定。

路径选择使用未取整的内部成本。展示时先将每一个路线步骤四舍五入到整分钟，且至少一分钟，再相加为每人总时间，使详情各步骤与标题一致。加权排名使用这个展示总时间，因此极近的模型成本可能在取整后并列。界面的“步行”包括进出站，换乘步骤单列；首次候车计入首段地铁，之后的候车计入换乘。商圈字段 `walkMinutes` 仅供商圈浏览粗略参考，不再叠加进路线；末段步行按终点坐标重新估计。

## 每人的驾车路线

驾车路线不受地铁接驳范围限制；不在地铁步行接驳范围内的有效出发坐标，也可以参与驾车推荐。驾车总用时由道路行驶时间与到店步行两部分组成，换乘次数为零。

| 离线粗估参数   | 取值                              |
| -------------- | --------------------------------- |
| 道路距离       | 球面直线距离 × 1.35 绕行系数      |
| 平均行驶速度   | 30 公里 / 小时                    |
| 道路用时       | `max(1, 道路距离 / 30 × 60)` 分钟 |
| 停车后到店步行 | 另加五分钟                        |

上述驾车数值都是用于比较地点的模型假设，未经道路实测或交通数据校准，不代表当前路况，也没有计入找车位的时间。离线驾车线仅连接出发点与商圈中心，用于位置示意，不表示真实道路。出发点与商圈中心相同时保留一分钟驾车与五分钟步行；驾车几何只有一个点，不伪造道路。

`DrivingRouteData` 包含 `districtId`、道路 `minutes`、`distanceKm` 和 WGS84 道路折线 `coordinates`。API 的道路分钟不包含到店步行。`rankDistricts(friends, strategy, drivingRoutes?)` 与 `planRoute(friend, district, drivingRoutes?)` 接受可选覆盖数据，其结构为 `Record<string, DrivingRouteData[]>`，键由 `drivingOriginKey(location)` 产生，为未舍入的 `lng,lat`。起点匹配后再按商圈 ID 查找，朋友 ID 不参与 API 路线归属；因此同一出发点可共享数据，改到另一个地址坐标后不会误用旧起点路线。

只有时间和距离为有限非负数、几何非空且每个经纬度有效的匹配数据才覆盖粗估，否则回退到离线模型。接口正常返回时，个人路线标记 `source: 'amap'`；离线路线标记 `source: 'estimate'`。驾车道路时间按步骤取整后至少一分钟，再加独立五分钟 `walk` 步骤，确保每人总用时等于详情各步之和。该步行步骤只有商圈目的地单点，实际停车处与餐厅入口未知，因此地图不会画出虚构的末段步行路线。

## 权重与三种策略

本次参加朋友 `i` 按其所选交通方式到某个商圈的估计总用时记作 `tᵢ`，通勤优先级为 `wᵢ`。地铁与驾车采用同一评分公式，其中驾车的 `tᵢ` 包含到店步行五分钟。界面权重可在 0.2–2.0 倍间调整，默认均为 1.0：数值越高，推荐越重视这个人的方便；愿意多通勤一段可调低。权重影响选址评分，不会改变真实时间，也不是最长通勤承诺。

计算加权平均 `A`、平均权重 `w̄`，以及归一化加权最长用时 `M`：

```text
A = Σ(wᵢ × tᵢ) / Σwᵢ
w̄ = Σwᵢ / 本次参加人数
M = max((wᵢ / w̄) × tᵢ)
```

所有商圈按所选策略的分数从低到高排序：

| 界面策略 | 分数                | 适合的目标                               |
| -------- | ------------------- | ---------------------------------------- |
| 综合最优 | `0.7 × A + 0.3 × M` | 兼顾整体通勤与最不方便的朋友             |
| 总耗时少 | `A`                 | 减少整体的加权通勤时间                   |
| 照顾最远 | `M + 0.1 × A`       | 优先压低加权最长用时，同时略考虑整体时间 |

例如甲 60 分钟、乙 30 分钟，原本两人的权重都是 1.0。若甲愿意多通勤，把甲调到 0.5，则甲的归一化加权用时为 40，乙也为 40；甲的行程仍显示 60 分钟。模型因此会更重视缩短乙的时间，有可能选择距离乙更近的商圈。

界面显示的平均、最长及每人时间使用未加权的通勤分钟数，其中平均值四舍五入到整分钟；评分中的权重只用于排名。将所有人的权重按相同比例缩放，不应改变排序。低权重也不会把某个人从计算中删除。评分完全相同按商圈 ID 稳定排序，避免界面在相同输入下跳动。

## 交互与缓存

路由模块最多缓存 128 个地铁起点最短路径树和 2048 条个人路线，仅保存在当前页面内存中。路线缓存键包含交通方式、起点坐标、起点地址、朋友 ID、商圈终点，以及有效驾车覆盖数据的时间、距离与几何内容；它不含权重或参加状态。这样切换交通方式、修改地点或取得新的道路数据后，会计算对应路线，离线粗估与 API 道路结果不会混用。修改权重或重新参加时可复用已有个人路线并重新评分，API 数据也可按同一出发点复用。缓存超过上限时移除最早插入的记录。

方案的浏览器保存由界面层负责，路由模块不读写 `localStorage`，也不发出网络请求。

## 适用范围

“最优”是当前候选商圈、接驳站集合和模型参数下的最优；它不是深圳任意地点的全局最优，也不衡量餐厅实时座位、消费、口味或营业状态。附近地铁候选有限，有时模型会漏掉需要步行更远但更快的实际路线。

步行距离近似没有道路网络，无法识别河流、围墙、天桥、过街限制和站内入口。商圈内选择不同餐厅也会改变最后一段步行。适合先找到共同区域，再用真实导航和餐厅信息确认细节。
